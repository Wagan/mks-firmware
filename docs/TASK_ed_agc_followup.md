П1. ПРЕДЕЛ ЧИСЛА ОТСЧЁТОВ НА КОМАНДУ — установить причину и исправить

Факт с железа: при N = 83 команда 0x44 отвечает нормально, при N = 84 плата не
отвечает вообще (хост не дожидается SYNC). Арифметика кадра: 2 байта SYNC +
1 LEN + 1 STATUS + 3N данных + 1 CRC, то есть 254 байта при N = 83 и 257 при
N = 84. Похоже на предел буфера ответа в 256 байт, но это ГИПОТЕЗА хоста, а не
установленный факт.

Требуется:
  а) найти в коде фактический размер буфера ответа и место, где он ограничивает
     длину кадра; привести файл:строка;
  б) объяснить, почему при превышении не возвращается ошибка, а ответа нет
     вовсе — если из кода это следует, показать где; если не следует, писать
     НЕ УСТАНОВЛЕНО;
  в) исправить проверку N в обработчике команды на фактический предел;
  г) исправить PROTOCOL_SPEC новой версией документа: указать верный предел и
     привести расчёт полной длины кадра, чтобы предел не пересчитывался заново
     из размера DATA.

Расширять буфер НЕ надо: 83 отсчёта на команду достаточно, хост набирает серию
несколькими командами.


П2. ЗАРЕЗЕРВИРОВАННЫЕ БИТЫ AGC_STAT1 — только сверка, без изменений кода

Факт с железа: младшие шесть бит (5-0) саб-регистра 0x23:1E во всех без
исключения отсчётах равны 18 (десятичное), на 162 400 отсчётах фона и на всех
опытных сериях. Биты 23-20 при этом всегда нули.

Требуется по DW1000 UM v2.17: сказано ли что-либо о битах 5-0 этого
саб-регистра — объявлены зарезервированными без указания значения, указано ли
значение по сбросу, или там описано какое-то поле, которое мы не учли.
Проверить также deca_regs.h на предмет маски, покрывающей эти биты.

Ответ «UM значения не указывает» — полноценный результат. Ничего не
додумывать: постоянство значения на 162 тысячах отсчётов само по себе ничего не
доказывает о назначении битов.
