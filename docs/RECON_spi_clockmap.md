# RECON — Тактирование и реальная скорость SPI к радиомодулям

**Автор:** Vagan Sarukhanov
**Дата:** 2026-07-27
**Тип:** РАЗВЕДКА (RECON). Только чтение кода, правок не вносилось.
**Задание:** `docs/TASK_recon_spi_clockmap.md`
**Проект:** mks-firmware (МКС, STM32F411 + 2× DWM1000)

> **Итог одной строкой.** По коду рабочий SPI к радио — **прескалер /32, 1.125 МГц**
> (и CubeMX-дефолт, и `set_slow` — оба /32; `set_fast` не вызывается). Это **совпадает**
> с выводом `RECON_raw_cir_monitor.md` Б6. Замер `read_ms = 1/2/3 мс` его **НЕ
> опровергает**: он невалиден по построению — `HAL_GetTick` заморожен, т.к. SPI-передача
> идёт с **замаскированными прерываниями** (`decamutexon → __disable_irq`), и SysTick в
> это время не тикает. Подробности — раздел СВЕРКА.

## ФАКТЫ

### Б1. Тактирование шин

**Тактовая (`Core/Src/main.c`, `SystemClock_Config`):**
- Источник: **HSE**, PLL от HSE (`main.c:144-147`). Частота HSE в коде численно не
  задаётся (задаётся в CubeMX/.ioc); для справки `board_config.h:34` — `BOARD_HSE_HZ =
  24000000U` (24 МГц). *(Само число HSE в `.c` не фигурирует — см. НЕ УСТАНОВЛЕНО.)*
- PLL: `PLLM = 12` (`main.c:148`), `PLLN = 72` (`:149`), `PLLP = RCC_PLLP_DIV2` (`:150`),
  `PLLQ = 3` (`:151`).
- Делители: `AHBCLKDivider = RCC_SYSCLK_DIV1` (`:162`), `APB1CLKDivider = RCC_HCLK_DIV2`
  (`:163`), `APB2CLKDivider = RCC_HCLK_DIV1` (`:164`).

**Расчёт частот (при HSE = 24 МГц по `board_config.h:34`):**
| Величина | Формула | Значение |
|---|---|---|
| VCO вход | 24 / PLLM(12) | 2 МГц |
| VCO | 2 × PLLN(72) | 144 МГц |
| SYSCLK | 144 / PLLP(2) | **72 МГц** |
| HCLK (AHB) | 72 / 1 | 72 МГц |
| **PCLK1 (APB1)** | 72 / 2 | **36 МГц** |
| **PCLK2 (APB2)** | 72 / 1 | **72 МГц** |
| (USB) | 144 / PLLQ(3) | 48 МГц |

**Правило удвоения APBx-таймерной частоты:** в `SystemClock_Config` (`main.c:131-170`)
и вообще в коде проекта **явно НЕ фигурирует** — задаются только делители. К SPI оно и
не относится: SPI тактируется от **PCLK** шины (APB1/APB2), не от таймерной ветви.
По памяти правило не подставляю (правило 3 задания).

**Какие SPI у радиомодулей и на какой шине:**
- `DW_M1_SPI = hspi2` → **SPI2** (`board_config.h:81`), `DW_M2_SPI = hspi3` → **SPI3**
  (`board_config.h:89`). Шины **раздельные** — HANDOFF §3 п.7 **подтверждён кодом**.
- SPI2/SPI3 — периферия **APB1** (`stm32f411xe.h:665-666`: `SPI2_BASE`/`SPI3_BASE` =
  `APB1PERIPH_BASE + …`). ⇒ тактовая шины **PCLK1 = 36 МГц** и для M1 (SPI2), и для
  M2 (SPI3).

### Б2. Прескалер, действующий в момент чтения аккумулятора

- **CubeMX-дефолт:** `MX_SPI2_Init` — `hspi2.Init.BaudRatePrescaler =
  SPI_BAUDRATEPRESCALER_32` (`main.c:233`) + `HAL_SPI_Init(&hspi2)` (`:238`).
  `MX_SPI3_Init` — `hspi3.Init.BaudRatePrescaler = SPI_BAUDRATEPRESCALER_32` (`main.c:271`)
  + `HAL_SPI_Init(&hspi3)` (`:276`). Оба вызываются на старте: `MX_SPI2_Init()`/
  `MX_SPI3_Init()` (`main.c:100-101`).
- **`set_slow` переустанавливает то же /32:** `s_spi->Init.BaudRatePrescaler =
  SPI_BAUDRATEPRESCALER_32` (`deca_port.c:103`) + `HAL_SPI_Init(s_spi)` (`:104`).
  Вызывается в `HandleINIT` для каждого живого модуля (`protocol.c:504`).
- **Другие записи `BaudRatePrescaler` / `HAL_SPI_Init` в `App/**` и `Core/**`
  отсутствуют** (grep по обоим деревьям дал только `main.c` — SPI1/2/3 инициализации —
  и `deca_port.c` — `set_slow`/`set_fast`). В `protocol.c` `HAL_SPI_Init` НЕ вызывается —
  ни `SET_PHY_CONFIG`, ни `RX_START`, ни `CIR_RAW_ARM` шину не переинициализируют.
- **`set_fast` (/4) не вызывается нигде** (grep `spi_set_fast` по репозиторию — только
  определение `deca_port.c:107` и прототип `deca_port.h:40`).

**Итог Б2:** на момент `dwt_readaccdata` `BR[2:0]` = **/32** и для M1, и для M2 (и
CubeMX-дефолт, и последний `set_slow` дают /32; ничто не переключает на fast). Тактовая
SPI = **36 МГц / 32 = 1.125 МГц** на обеих шинах.

### Б3. Делают ли set_slow / set_fast что-либо физически

Тела целиком (`deca_port.c:100-112`):
```c
void deca_port_spi_set_slow(void)
{
    if (!s_spi) return;
    s_spi->Init.BaudRatePrescaler = SPI_BAUDRATEPRESCALER_32; /* подобрать */
    HAL_SPI_Init(s_spi);
}
void deca_port_spi_set_fast(void)
{
    if (!s_spi) return;
    s_spi->Init.BaudRatePrescaler = SPI_BAUDRATEPRESCALER_4;  /* подобрать */
    HAL_SPI_Init(s_spi);
}
```
- Обе пишут в поле структуры **И вызывают `HAL_SPI_Init(s_spi)`** ⇒ **НЕ no-op**: они
  реально перепрограммируют периферию (CR1.BR). Проблема NOTE — **не** «переключение не
  работает», а именно «`set_fast` **не вызывается**». Формулировка `NOTE_spi_set_fast_unused.md`
  по сути верна.
- **Важное уточнение:** даже если бы `set_slow` вообще не звался, шина всё равно осталась
  бы на /32 — **CubeMX сам инициализирует SPI2/SPI3 на /32** (`main.c:233,271`). То есть
  /32 — это состояние «по умолчанию из коробки», а не следствие только `set_slow`.
- **Вызовы `set_slow`** (grep, не по памяти): `App/bringup.c:40` и `App/protocol/protocol.c:504`
  (в `HandleINIT`). Живой командный путь INIT → `protocol.c:504`. (Компилируется ли
  `bringup.c` в текущей сборке — см. НЕ УСТАНОВЛЕНО; на итог не влияет — оба места /32.)
- Вызовов `set_fast` — **ноль**.

### Б4. Способ передачи и кто ждёт

Путь чтения аккумулятора: `dwt_readaccdata` (`deca_device.c:712-720`) → `dwt_readfromdevice`
(`:717`) → `readfromspi` (`deca_port.c:148-166`).

`readfromspi` (`deca_port.c:148-166`):
- `decamutexon()` (`:153`) → **`__disable_irq()`** (`deca_port.c:184`) — маскирует ВСЕ
  прерывания на время транзакции; восстановление в `decamutexoff` (`:191-196`).
- `HAL_SPI_Transmit(header, SPI_TIMEOUT_MS)` (`:156-157`), затем
  `HAL_SPI_Receive(body, SPI_TIMEOUT_MS)` (`:159-160`).
- `SPI_TIMEOUT_MS = 5` (`deca_port.c:120`).
- **Опрос (polling), НЕ прерывания и НЕ DMA.** HAL-функции крутят флаги RXNE/TXE в цикле
  (`stm32f4xx_hal_spi.c` — `HAL_SPI_Receive`, tickstart-таймаут `:1028/:1052`).

**Что это значит (факт):** транзакция занимает **и шину, и процессор** (CPU спинит в
polling-цикле HAL), **и вдобавок держит прерывания замаскированными** всё время. Ни
overlap, ни вытеснение невозможны. DMA не используется. Для обнаружителя на 5 модулях это
самый жёсткий из ограничений: один полный съём монополизирует ядро и глушит IRQ на всё
время передачи.

### Б5. Сколько SPI доступно и сколько занято

- По заголовку `stm32f411xe.h`: **5 SPI** — `SPI1_BASE` (APB2, `:683`), `SPI2_BASE`
  (APB1, `:665`), `SPI3_BASE` (APB1, `:666`), `SPI4_BASE` (APB2, `:684`), `SPI5_BASE`
  (APB2, `:690`).
- Инициализируются в проекте: `MX_SPI1_Init`/`MX_SPI2_Init`/`MX_SPI3_Init` (`main.c:100-101`
  + `MX_SPI1_Init` рядом) — **3 из 5**. `MX_SPI4/5_Init` в коде нет.
- Назначение на МКС (`board_config.h`): SPI1 = EEPROM M95080 (`:97`, **не радио**, APB2 =
  72 МГц), SPI2 = M1 (`:81`), SPI3 = M2 (`:89`). Радио — на двух РАЗДЕЛЬНЫХ шинах APB1.
- SPI4/SPI5 в коде не заняты. Есть ли они физически разведены на плате — вопрос схемы, не
  кода → НЕ УСТАНОВЛЕНО (разведка по железу в этот таск не входит).

## СВЕРКА С ЗАМЕРОМ

**Расчёт по установленной частоте (Б1/Б2): SPI = 1.125 МГц, /32.**

Объём чтения полного аккумулятора (PRF64, 1016 отсч.): `dwt_readaccdata(buf, 1016*4+1, 0)`
(`protocol.c:1374-1375` — `PROTOCOL_CaptureRawCIR`). По проводу за одну `readfromspi`:
- header **1 байт** (offset 0 → без sub-index, `deca_device.c:1022-1024`);
- тело **4065 байт** (dummy 1 + 4064 данных).
- Итого **4066 байт**.

Время (8 бит/байт, встык): `4066 × 8 / 1.125e6 = `**`28.9 мс`** (теор. минимум по
битовому клоку; polling-оверхед HAL и `_dwt_enableclocks` (мелкие транзакции
`deca_device.c:715,719`) добавят сверху). Ожидание: **≈29 мс и более**.

**Замер:** `read_ms = 1 / 2 / 3 мс` (три съёма подряд, PRF64, событие RXSFDD), снят
`HAL_GetTick` вокруг `dwt_readaccdata` (`protocol.c:1374` `t0`, `:1376` `dt`, `:1380`
запись).

**Сходится ли: НЕТ.** Расчёт ~29 мс, замер 1–3 мс — расхождение ~10–30×.

**Причина расхождения установлена по коду — замер невалиден (не подгонка, а объяснение):**
1. `read_ms` считается как `HAL_GetTick() - HAL_GetTick()` вокруг чтения
   (`protocol.c:1374-1376`).
2. `HAL_GetTick()` возвращает `uwTick` (`stm32f4xx_hal.c:323-325`).
3. `uwTick` инкрементируется **только** в `HAL_IncTick` (`stm32f4xx_hal.c:312-314`),
   который зовётся из `SysTick_Handler` (`stm32f4xx_it.c:183,188`) — т.е. по прерыванию
   SysTick.
4. Само чтение (`dwt_readaccdata → readfromspi`) идёт под `decamutexon()` →
   **`__disable_irq()`** (`deca_port.c:153,184`): на всё время передачи прерывания
   замаскированы ⇒ SysTick не срабатывает ⇒ `uwTick` **заморожен**.
5. ⇒ `HAL_GetTick()` до и после передачи возвращает почти одно и то же ⇒ `read_ms`
   **сильно недосчитывает** реальное время. Наблюдаемые 1–3 мс — это тик, «проскочивший»
   в коротких ОКНАХ между под-транзакциями внутри `dwt_readaccdata` (READ_ACC_ON /
   само чтение / READ_ACC_OFF — три отдельных `readfromspi`/`writetospi`, между которыми
   IRQ кратко разрешены), а не длительность передачи.

**Побочное следствие (тем же механизмом):** HAL-таймаут `SPI_TIMEOUT_MS = 5` на
`HAL_SPI_Receive` при /32 (передача ~29 мс) **не срабатывает** — HAL сверяет
`(HAL_GetTick() - tickstart) >= Timeout` (`stm32f4xx_hal_spi.c:1028,1052`), а `uwTick`
заморожен той же маской IRQ ⇒ условие таймаута никогда не истинно ⇒ чтение доходит до
конца (4066 Б не обрезаются), несмотря на 5-мс параметр. Это объясняет, почему съём на
/32 всё же отдаёт полный CIR, а не обрывается на 5 мс.

**Вывод СВЕРКИ:** цифра `1.125 МГц (/32)` из `RECON_raw_cir_monitor.md` Б6 —
**корректна** и подтверждается кодом заново. Замер `read_ms` её не опроверг; сам замер
методически несостоятелен (меряет wall-clock замороженным тиком). Инференс «4066 Б за
2 мс ⇒ 16 Мбит/с» **неверен**, т.к. 2 мс — не реальное время передачи.

> **Прямое следствие для архитектуры обнаружителя.** Окно слепоты приёмника на один
> полный съём ≈ **29 мс** (а не ~2 мс). Вывод `RECON_raw_cir_monitor.md` — «только
> разовый съём, непрерывный поток полного CIR обесценивает замер» — **остаётся в силе**.
> Непрерывный полный съём на текущей скорости невозможен. Обсуждать непрерывный режим
> имеет смысл только ПОСЛЕ включения `set_fast` и **валидного** перезамера (см. ниже).

## ГИПОТЕЗЫ (не факты)

- **ГИПОТЕЗА.** При включении `set_fast` (/4 → 36/4 = 9 МГц) съём 4066 Б займёт
  `4066×8/9e6 ≈ 3.6 мс` — окно слепоты уменьшится ~8×, но останется соизмеримым с
  межкадровым интервалом; «непрерывный полный съём» станет пограничным, не бесплатным.
  Проверяется валидным замером (не через `HAL_GetTick`).
- **ГИПОТЕЗА.** Валидно измерить время `dwt_readaccdata` можно **DWT CYCCNT** (счётчик
  тактов ядра), который работает при замаскированных IRQ, — в отличие от `HAL_GetTick`.
  Требует инициализации DWT (в проекте не включён — см. НЕ УСТАНОВЛЕНО).
- **ГИПОТЕЗА.** Значения `1/2/3 мс` монотонно растут по трём съёмам, возможно, из-за
  накопления тика в межтранзакционных окнах или фоновых USB-IRQ между съёмами; это
  согласуется с «замороженным тиком + редкие окна», но точная причина конкретных чисел
  по коду не устанавливается.

## НЕ УСТАНОВЛЕНО

1. **Численное значение HSE в `.c`-коде.** `SystemClock_Config` не содержит числа HSE
   (оно в `.ioc`/CubeMX). Расчёты выше опираются на `board_config.h:34` (24 МГц,
   справочно) — само значение PLL-входа в исполняемом коде не задаётся явным числом.
   Чего не хватает: содержимого `.ioc` / регистрового значения (в исходниках `.c` его нет).
2. **Компилируется ли `App/bringup.c`** (его `set_slow` на `:40`). Это настройка
   «Exclude from Build» в `.cproject`/IDE, а не факт из `.c`. На итог не влияет (оба места
   дают /32). Чего не хватает: разбора build-конфига (в таск чтения кода не входит).
3. **Реальное (wall-clock) время `dwt_readaccdata`.** Прямым замером не установлено: в
   проекте нет валидного таймера, работающего при `__disable_irq` (DWT CYCCNT не включён;
   `HAL_GetTick` заморожен). ~29 мс — расчёт, не измерение. Чего не хватает: замера через
   CYCCNT/внешний таймер/логический анализатор.
4. **Физическая разводка SPI4/SPI5 на плате МКС.** По коду они не заняты; есть ли они на
   плате — вопрос схемы, не кода (разведка по железу вне таска).
