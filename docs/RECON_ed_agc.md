## ФАКТЫ

### П1. AGC_STAT1 (0x23:1E) — поля EDG1 и EDV2

**UM §7.2.36.9 (печ.124/PDF125):**
- Длина саб-регистра — **3 октета (24 бита)**: «sub-register 0x1E is a **24-bit** status register
  for the measurement function of the AGC».
- **EDG1** — «reg:23:1E **bits:10-6**» → смещение **6**, ширина **5 бит**. Дословно: «This
  **5-bit gain value** relates to input noise power measurement. EDG1 can be used in conjunction
  with the EDV2 value to give a measure of the background in-band noise energy level. This might be
  used for an **Energy Detect (ED channel scan)** … MLME-SCAN request primitive.»
- **EDV2** — «reg:23:1E **bits:19-11**» → смещение **11**, ширина **9 бит**: «This **9-bit value**
  relates to the input noise power measurement.»
- Биты 23-20 и 5-0 — reserved.
- **Порядок байт — LE** (общее правило §2.2.1, печ.11/PDF12: «octets … transferred … beginning
  with the low-order octet»; отдельного упоминания для 0x23:1E нет).

**Код (согласуется по битам):** `AGC_STAT1_OFFSET 0x1E`, `AGC_STAT1_LEN (3)`, `AGC_STAT1_MASK
0x0FFFFF` (deca_regs.h:626-628); `AGC_STAT1_EDG1_MASK 0x0007C0` (биты 10-6, deca_regs.h:629,
комментарий «5-bit gain value … input noise power measurement»); `AGC_STAT1_EDG2_MASK 0x0FF800`
(биты 19-11, deca_regs.h:630, «9-bit value … input noise power measurement») — это поле UM зовёт
**EDV2** (см. расхождение выше).

### П2. DIS_AM (0x23:02 AGC_CTRL1)

**UM §7.2.36.2 (печ.122/PDF123):**
- 0x23:02 — **2 октета (16 бит)**: «sub-register 0x02 is a **16-bit control register** for the
  measurement function of the AGC».
- **DIS_AM** — «reg:23:02 **bit:0**» → смещение **0**, ширина **1 бит**. «**Disable AGC
  Measurement.** The DIS_AM bit is **set by default** to disable the AGC measurement function.»
- Остальные биты **15-1 — reserved** (= 0). Reset-значение регистра — **0x0001** (DIS_AM=1,
  reserved=0). RMW не требуется явно: т.к. reserved=0 по сбросу, регистр можно писать целиком
  (**0x0001** = заморожено, **0x0000** = измерение включено) при условии, что reserved остаются 0.
  *(Явной фразы «пишите весь регистр» в UM нет — вывод из reset-карты и пометки reserved=0.)*

**Код:** `AGC_CTRL1_OFFSET 0x02`, `AGC_CTRL1_LEN (2)`, `AGC_CTRL1_MASK 0x0001`, `AGC_CTRL1_DIS_AM
0x0001` (deca_regs.h:602-605; комментарий «The DIS_AM bit is set by default»).

**Пишет ли наша инициализация в 0x23:02 — НЕТ.** `dwt_configure` пишет AGC только по смещениям
**0x0C** (`AGC_CFG_STS_ID, 0xC`) и **0x04** (`AGC_CFG_STS_ID, 0x4`) — deca_device.c:535-536
(AGC_TUNE1/2). Смещение **0x02 (AGC_CTRL1/DIS_AM) не трогается** ни в `dwt_configure`, ни где-либо
ещё в драйвере/`App` (grep `AGC_CTRL1`/`DIS_AM`/`0x23:02` по `{App,Drivers}` — только определения в
`deca_regs.h`, ни одной записи). ⇒ **После нашей штатной настройки PHY DIS_AM остаётся на сбросовом
дефолте = 1**, т.е. функция измерения АРУ **выключена**; для энергоскана её надо снять в 0.

### П3. Готовые средства в драйвере

**Функции чтения AGC_STAT1 или расчёта энергии по EDG1/EDV2 — НЕТ.** Поиск `AGC_STAT1`,
`AGC_CTRL1`, `DIS_AM`, `EDG1`, `EDV2`, `0x23` по `Drivers/decadriver/*` и `App/**` даёт **только
определения масок/смещений в `deca_regs.h`** (строки 595-630) — ни одной функции, читающей 0x23:1E
или вычисляющей noise по Figure 27. В `deca_device_api.h` таких прототипов нет.

**Конкретные вызовы (образцы уже используемых в нашем коде саб-регистровых доступов):**
- Чтение саб-регистра по смещению (наш образец): `dwt_read16bitoffsetreg(DRX_CONF_ID,
  RXPACC_NOSAT_OFFSET)` — `protocol.c:1516`. Функция `dwt_read32bitoffsetreg` определена в
  `deca_device.c:1063`.
- Для **чтения AGC_STAT1** (3 октета / 24 бита): `dwt_read32bitoffsetreg(AGC_CTRL_ID,
  AGC_STAT1_OFFSET)` — вернёт 4 байта, значимы младшие 20 бит (маска `AGC_STAT1_MASK 0x0FFFFF`);
  `EDG1 = (v & 0x0007C0) >> 6`, `EDV2 = (v & 0x0FF800) >> 11`.
- Для **записи DIS_AM** (16-бит саб-регистр): `dwt_write16bitoffsetreg(AGC_CTRL_ID,
  AGC_CTRL1_OFFSET, 0x0000/0x0001)` — образец такого вызова (тот же тип на регистре AGC):
  `dwt_write16bitoffsetreg(AGC_CFG_STS_ID, 0x4, …)` — `deca_device.c:536`.

*(Всё — константы из `deca_regs.h`, не хардкод. `AGC_CTRL_ID == AGC_CFG_STS_ID == 0x23`,
deca_regs.h:598-600.)*

### П4. Источник энергии и скважность (риск ложного отрицания)

**Окно измерения — 32 мкс** (UM §7.2.36.2, шаг (d): «Wait 32 µs for the AGC to settle»).

**Тайминг кадра** (кан.2, 110 кбит/с, преамбула 1024, PRF 64, PAC 32, payload 5 Б) — по числам,
которые ЕСТЬ в UM:
- Символ преамбулы **Tpsym(PRF64) = 1017.63 нс** (Table 60, печ.217/PDF218; сноска §7.2.10 печ.75).
- Преамбула: 1024 × 1017.63 = **1 042 053 нс ≈ 1042.05 мкс**.
- **SFD для 110 кбит/с = 64 символа** (§4.1.3 печ.32; §10.3 печ.217), символ SFD = Tpsym →
  64 × 1017.63 = **65 128 нс ≈ 65.13 мкс**.
- **PHR = 19 бит** (§10.4, печ.217), передаётся «just over 120 kbps» — **длительности в нс UM не
  даёт числом** → НЕ УСТАНОВЛЕНО.
- **Данные:** 5 Б payload + 2 Б FCS = 56 бит; **длительности символа данных 110 кбит/с в нс в UM
  нет** → НЕ УСТАНОВЛЕНО.

**Итог:** полностью посчитать время кадра из UM **нельзя** (нет длительностей PHR и данных).
Достоверный **нижний предел** (преамбула + SFD) = **1107.18 мкс ≈ 1.107 мс**; реальный кадр длиннее.

**Скважность (нижняя оценка, доля времени «энергия в эфире» = airtime/период):**
- `txperiodic` **100 мс** → ≥ 1107.18 мкс / 100 мс = **≥ 1.1 %**.
- `txperiodic` минимум **5 мс** (`TX_PERIOD_MIN_MS 5`, protocol.c:1122; проверка `period <
  TX_PERIOD_MIN_MS → INVALID_PARAM`, protocol.c:1209) → ≥ 1107.18 мкс / 5 мс = **≥ 22.1 %**.

Т.е. одиночное 32-мкс окно ловит энергию импульсной `txperiodic` лишь в ~1 % случаев (100 мс) —
~22 %+ (5 мс). Для одиночного снимка это высокий риск ложного отрицания (энергия была, но мимо окна).

**Непрерывная передача (документирована и в UM, и в драйвере; в нашей прошивке НЕ используется):**
- **Continuous Wave (CW)** — немодулированная несущая. UM §7.2.43.7 (рег 0x2A:0C TC_PGTEST=0x13,
  печ.160) / §8.1.1 (печ.202-203). Драйвер: `dwt_configcwmode(uint8 chan)` — `deca_device.c:3122`
  (прототип `deca_device_api.h:1433`).
- **Continuous / repeating frame (Tx Power Spectrum, TX_PSTM)** — повтор кадров back-to-back.
  UM §7.2.48.15 (рег 0x2F:24 DIAG_TMC, бит TX_PSTM bit4, печ.191): «repeating transmission of the
  data from the TX_BUFFER … to send back-to-back frames the time value should be set to the frame
  duration.» Драйвер: `dwt_configcontinuousframemode(uint32 framerepetitionrate)` —
  `deca_device.c:3174` (прототип `deca_device_api.h:1448`).
- В `App/**` **ни `dwt_configcwmode`, ни `dwt_configcontinuousframemode` не вызываются** (grep).

**Выбор для Вагана (чем создавать энергию под 32-мкс окно) — см. «ВОПРОСЫ К ВАГАНУ».**

### П5. Транспорт результата

**Свободный код команды.** По `protocol.h` (коммит fc893d0) заняты: 0x00-0x03, 0x10-0x11,
0x20-0x22, 0x30-0x31, **0x40-0x43** (0x43 = `CMD_CIR_RAW_ARM`, protocol.h:53-54), 0x50-0x51,
0x60-0x61. Новых после 0x43 нет. **Ближайший свободный — `0x44`** (также свободны 0x12-0x1F,
0x23-0x2F, 0x32-0x3F, 0x44-0x4F, 0x52-0x5F, 0x62+).

**Формат командного кадра** (PROTOCOL_SPEC §2/§3): запрос `SYNC(2) LEN(1) CMD_ID(1) PARAMS(0..) CRC(1)`,
`LEN = CMD_ID+PARAMS` (u8) → **PARAMS ≤ 254 Б**; ответ `SYNC(2) LEN(1) STATUS(1) DATA(0..) CRC(1)`,
`LEN = STATUS+DATA` (u8) → **DATA ≤ 254 Б**.

**Сколько отсчётов EDG1/EDV2 в один ответ** (пара 14 значимых бит: EDG1 5 + EDV2 9; DATA ≤ 254 Б):
- отсчёт = **2 Б** (упаковка EDG1+EDV2 в 14 бит) → **≤ 127** отсчётов;
- отсчёт = **3 Б** (сырой AGC_STAT1, 24 бита) → **≤ 84** отсчёта;
- отсчёт = **4 Б** (сырой регистр u32) → **≤ 63** отсчёта.
*(Кодировка — вопрос будущей реализации; здесь только арифметика по размеру пары из П1.)*

**Место в приёмном цикле без конфликта — в текущем цикле ОТСУТСТВУЕТ (обосновано кодом).**
`PROTOCOL_PollRadio` (protocol.c:1473-1547) — владелец **непрерывного** приёма: при `rx_active`
читает `SYS_STATUS` (1479), по RXFCG читает кадр и **перевзводит `dwt_rxenable`** (1537 район),
по ошибке — `dwt_rxreset`+`dwt_rxenable` (1543-1544). Процедура энергоскана (UM §7.2.36.2) —
это иная последовательность над тем же приёмником: `DIS_AM=0` → `RXENAB` → ждать 32 мкс →
`DIS_AM=1` → чтение → **`TRXOFF`** (шаг g, приёмник выключается). Она (а) требует контролируемого
32-мкс окна и завершается **выключением** приёмника, что противоречит непрерывному `rxenable`
в PollRadio; (б) толкает DIS_AM, который в остальное время оставлен в дефолте; (в) упирается в
неизвестность П6 (можно ли принимать при DIS_AM=1). ⇒ энергоскан — **отдельная операция над
приёмником**, а не вставка в текущий цикл непрерывного приёма; бесконфликтной точки внутри
`PROTOCOL_PollRadio` при активном `rx_active` нет.

### П6. Конфликт заморозки и приёма (DIS_AM=1)

**Явного утверждения в UM НЕ НАЙДЕНО.** Что сказано (§7.2.36.2): DIS_AM отключает **только функцию
измерения АРУ** («Disable AGC Measurement … the AGC measurement function»), это **дефолтное**
состояние, рекомендованное для экономии («To save power … set DIS_AM bit to 1»). При этом сама
процедура энергоскана после `DIS_AM=1` предписывает шаг (g) `TRXOFF` — т.е. внутри сценария приём
затем **выключают**, а не продолжают. Прямой фразы «приёмник продолжает нормально принимать кадры
при DIS_AM=1» или «приём при заморозке недопустим» в тексте нет (просмотрены §7.2.36.2, §7.2.36.9,
§4.1, §4.7). ⇒ **вопрос замера на железе** (вынесен ниже).

## ГИПОТЕЗЫ (вывод из документов, не прямые утверждения)

1. **ГИПОТЕЗА (энергоскан не зависит от совпадения кода преамбулы).** UM позиционирует EDG1/EDV2
   как «background in-band noise energy level» для «Energy Detect (ED channel scan)» (§7.2.36.9) —
   это измерение энергии в полосе, а не корреляция с кодом преамбулы. *Шаг вывода:* «измеряется
   энергия в полосе» ⇒ «регистрируется независимо от того, совпал ли код и был ли штатный захват».
   Прямой связки «даёт контраст пустой эфир / активность при чужом коде» UM не утверждает — это и
   есть предмет будущего замера (да/нет из контекста задания).
2. **ГИПОТЕЗА (приём при DIS_AM=1 идёт штатно).** Т.к. DIS_AM=1 — дефолт при любом обычном приёме
   и отключает лишь измерялку (П6), по логике текста приём кадров при DIS_AM=1 работает. Дословно
   не заявлено ⇒ гипотеза, требует замера.
3. **ГИПОТЕЗА (полное время кадра ≫ 32 мкс, поэтому непрерывный источник надёжнее).** Даже
   вычислимая часть (преамбула+SFD = 1.107 мс) на порядки больше 32-мкс окна, а импульсная
   `txperiodic` даёт низкую скважность (П4). *Шаг вывода:* «airtime ≪ период» ⇒ «одиночное окно
   чаще всего мимо». Отсюда CW/continuous-frame предпочтительнее для наполнения окна — но это выбор
   Вагана, не рекомендация (см. ниже).

## НЕ УСТАНОВЛЕНО (с перечнем просмотренного)

1. **Длительность PHR и символа данных 110 кбит/с в нс** — UM даёт только «PHR … just over
   120 kbps» и «110 kbps» с оговоркой «0.87 factor … Reed Solomon» (§10.2, печ.215), без чисел в нс.
   ⇒ полное время кадра из UM не считается. Просмотрено: §3, §4.1, §9.6, §10.2-10.4, Table 60.
2. **Приём кадров при DIS_AM=1** (П6) — прямой формулировки нет. Просмотрено: §7.2.36.2/.9, §4.1, §4.7.
3. **Внутри-UM расхождение PHR 19 бит (§10.4/Figure 33) vs 21 бит (Figure 10, §3.1)** — на расчёт
   не влияет (длительности всё равно нет), но зафиксировано. Авторитетно §10.4 = 19 бит.

## ВОПРОСЫ К ВАГАНУ (до реализации)

1. **Имя 9-битного поля: EDV2 (UM §7.2.36.9) vs EDG2 (`deca_regs.h:630`).** Биты/смысл совпадают
   (19-11, «input noise power»). По правилу 5 не выбираю имя сам — какое использовать в коде/хосте
   и отчётности? (Предлагается зафиксировать «EDV2 по UM; в драйвере это `AGC_STAT1_EDG2`».)
2. **Чем создавать энергию в эфире под 32-мкс окно** (П4) — выбор, не рекомендация:
   - (а) **CW** (`dwt_configcwmode`) — непрерывная **немодулированная несущая**, ~100 % энергии в
     окне, но это не UWB-кадр (годится ли как «активность в канале» для теста?);
   - (б) **continuous frame** (`dwt_configcontinuousframemode` / TX_PSTM) — back-to-back **кадры**,
     ~100 % скважность, реалистичная UWB-энергия;
   - (в) оставить импульсную `txperiodic` и усреднять много 32-мкс снимков (низкая вероятность
     попадания: ~1 % при 100 мс, ~22 %+ при 5 мс).
3. **Где выполнять измерение** (П5/П6): бесконфликтной точки в текущем непрерывном приёме
   (`PROTOCOL_PollRadio`) нет. Энергоскан завершается `TRXOFF`. Приемлемо ли, что команда
   энергоскана временно забирает приёмник (выключает непрерывный приём на время измерения), или
   нужен режим «скан только когда `rx_active`=0»?
