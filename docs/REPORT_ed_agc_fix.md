## Симптом (с железа)

`CMD_ED_AGC_SCAN` (0x44): при `N=83` команда отвечает нормально, при `N=84` плата не
отвечает вовсе (хост не дожидается SYNC), ошибка при этом не возвращается.

## (а) Фактический ограничитель — 8-битная длина пакета, а НЕ размер буфера

Буфер ответа сам по себе **не мал**: `PROTOCOL_BuildResponsePacket` собирает пакет в
`static uint8_t packet[PROTOCOL_MAX_PACKET]` (protocol.c:136), где
`PROTOCOL_MAX_PACKET = 2+1+1+PROTOCOL_MAX_PAYLOAD+1 = 260` (protocol.c:34;
`PROTOCOL_MAX_PAYLOAD = 255`, protocol.h:24). 260 байт вмещают и кадр N=84 (257 Б).

Ограничивает **тип длины/индекса пакета — `uint8_t`**:
- `uint8_t index = 0;` (protocol.c:138) — индекс записи в пакет;
- параметр `uint8_t* packet_len` и `*packet_len = index;` (protocol.c:134, :152);
- отправка: `CDC_Transmit_FS(packet, packet_len)` (protocol.c:162,166), `packet_len` — `uint8_t`.

Полный кадр = `SYNC(2)+LEN(1)+STATUS(1)+3N+CRC(1) = 5+3N`.

**N=84 (кадр 257 Б):** после `memcpy` данных `index += data_len` = 4 + 252 = **256**, а
`index` — `uint8_t` → переполнение до **0**. Далее CRC пишется в `packet[0]` (затирает
`SYNC0=0xAA`), `index`→1, `*packet_len = 1`. `CDC_Transmit_FS(packet, 1)` шлёт **один
байт** — хост не видит валидного SYNC. Кадр-ответ разрушен переполнением индекса.

**N=83 (кадр 254 Б):** `index` = 4 + 249 = 253, CRC в `packet[253]`, `packet_len = 254`
(≤255, помещается в `uint8_t`) — кадр валиден, ответ уходит.

Отсюда предел: кадр обязан быть **≤255 байт** → `5 + 3N ≤ 255 → N ≤ 83`. Совпадает с
железом (83 — да, 84 — нет).

## (б) Почему нет ошибки и нет ответа

Из кода это **следует прямо** (не НЕ УСТАНОВЛЕНО): обработчик возвращает `STATUS_OK`,
`PROTOCOL_BuildResponsePacket` не имеет проверки переполнения `index`/`packet_len` и
при кадре ≥256 Б молча портит пакет и обрезает длину (см. (а), protocol.c:138,146-152).
`PROTOCOL_SendResponse` шлёт получившиеся `packet_len` байт без проверки успеха
(protocol.c:159-167). Итог: ошибка не формируется (статус OK), а «ответ» — это 1
испорченный байт, который хост не распознаёт как кадр. Ветки, возвращающей ошибку при
длинном DATA, в пути ответа нет.

## (в) Что изменено (только проверка N в обработчике)

`App/protocol/protocol.c` (под `#ifdef ED_AGC_SCAN`):

- `ED_AGC_MAX_SAMPLES` пересчитан **из полного кадра ответа**, а не из размера DATA:
  ```c
  #define ED_AGC_RESP_FRAME_MAX  255u  /* потолок кадра из-за uint8_t длины/индекса */
  #define ED_AGC_MAX_SAMPLES     ((ED_AGC_RESP_FRAME_MAX - 5u) / ED_AGC_SAMPLE_BYTES)  /* = 83 */
  ```
  Было `(254u / ED_AGC_SAMPLE_BYTES) = 84` (ошибочно считалось из DATA≤254, не учитывая
  полный кадр и uint8_t-длину). Стало **83**.
- Существующая проверка `if (n == 0u || n > ED_AGC_MAX_SAMPLES) return STATUS_INVALID_PARAM;`
  теперь отсекает `N=84` **штатной ошибкой** `INVALID_PARAM` (а не молчаливым разрушением
  кадра). Буфер отсчётов `buf[ED_AGC_MAX_SAMPLES*3]` уменьшился 252→**249** Б.

Буфер ответа **не расширялся** (по заданию); `PROTOCOL_BuildResponsePacket`,
`PROTOCOL_PollRadio`, процедура измерения — **не тронуты**.

`docs/PROTOCOL_SPEC.md` → **v1.9**: §8 предел `N ≤ 83` с расчётом полного кадра
(`5+3N ≤ 255`) и причиной (uint8_t-длина); §6 «1..83»; запись в истории.

## ВОПРОС К ВАГАНУ (вне рамок этой правки — не трогал)

Переполнение `uint8_t index`/`packet_len` в `PROTOCOL_BuildResponsePacket` — **общая**
особенность, а не только ЭД: любой ответ с полным кадром ≥256 Б (DATA ≥ 251) молча
разрушится так же. В частности **`GET_CIR` (0x41)** при максимуме (DATA = 6+62*4 = 254 Б
→ кадр 259 Б) попадёт в тот же дефект. Это продуктовый путь, задание его чинить не
поручало и запрещает рефакторинг вне флага — поэтому не трогал. Нужно ли отдельное
задание на исправление длины пакета в `PROTOCOL_BuildResponsePacket` (uint8→uint16) и
проверку `GET_CIR`?
